# 悬浮翻译：复杂分片与自动刷新独立验证计划

日期：2026-11-02（Asia/Shanghai）\
基线：0.4.0 / `87179c6`。关联：[0.5.0 详细设计](next-stage-detailed-design.md)。

本计划定义两个后续技术验证任务，本轮只设计，不编写或执行原型。二者独立于 G1/G2/G3；即使结论是不实施，也不会阻塞核心版本。验证通过仅表示值得进入后续实现设计，不自动获得加入安装包或开启默认行为的授权。

## 1. 公共执行约束与证据

- 后续验证使用单独分支/隔离测试入口，生产默认路径保持原行为。不建立额外公开配置让未验证逻辑进入正常请求。
- 先使用自写/公开夹具、真实语言服务和 fake transport；这些验证不需要真实付费 API。
- 测试只操作明确的夹具、测试 profile 与测试窗口；不修改用户日常工作区的信任、实验 API 设置或密钥。
- 每项输出“通过 / 有条件通过 / 不通过 / 环境不足无法判断”，附 VS Code/OS/语言服务版本、源码基线、用例结果、请求计数、截图或录像、剩余限制。
- 可见 UI 真值可使用现有测试专用 renderer/CDP 手段观察；产品实现不能依赖远程调试端口、DOM 注入、访问编辑器私有对象或定时模拟鼠标。
- 现有 macOS 结果与新 Windows 结果分别记录，不能把一个平台通过当所有平台通过。

## 2. G4：复杂 Markdown 分片局部翻译

### 2.1 问题与验证假设

当前 `prepareTakeover` 以整个来源片段判断能否安全重建。真实 Java `command:java.open.file` 链接可能使同一片段中的普通说明也保持英文；现有 `test/integration/languages.ts` 已将此作为保真行为断言。

验证问题：**能否把独立的安全顶层块翻译出来，同时保留特殊块的原始交互、安全属性和可见结构？**

第一轮只针对实验接管中的混合 MarkdownString；不扩展稳定追加策略，不处理任意 HTML，不拆同一句内部的链接周边文本。必须至少改善一个当前确实整片保留的真实 Java 样本，不能只让本来就可译的样本通过。

### 2.2 候选分片策略

1. 使用现有 AST 与源码 offset，建立顶层块的有序计划。每项是“可重建普通块”或“必须保留的源块”。
2. 独立普通块仍经过现有 `extractMarkdown`、占位符协议和输出校验；译文单独构造成 `isTrusted=false`、`supportHtml=false`、`supportThemeIcons=false` 的 MarkdownString。
3. 特殊块使用原始源码切片，不能经过 stringify 重写再自称原样。按来源复制其确有必要的元数据；不把生成文字并入这个对象。
4. 跨块依赖按最小封闭容器整体保留；不能证明封闭时整片保留。任何源码 offset 缺失、引用定义跨分片、列表/引用/表格内部混合都先保守回退。
5. 字符预算按原文顺序统一计算，不能每切一块重新获得完整预算；请求仍由既有协调器合并调度。
6. 输出保持原块顺序；paired 模式仅为可译块形成原文后接译文，translationOnly 仅替换可译块。保留块只能出现一次，不能复制整份源片段兜底造成重复。

拟议实验数据结构（仅用于验证边界，不是确定生产接口）：

```ts
type FragmentPart =
  | { kind: 'translate'; sourceStart: number; sourceEnd: number; text: string }
  | { kind: 'preserve'; sourceStart: number; sourceEnd: number; reason: PreserveReason };
// 所有 part 均隶属唯一 sourceIndex，源元数据来自该来源。
// 引用/容器边界无法闭合则返回 preserveWholeFragment。
```

### 2.3 信任与排版的关键证明

“特殊块原对象保留”对切片不成立：切片是新 MarkdownString，必须验证它没有改变原本链接解析和信任范围。

| 项目 | 必须证明 |
| --- | --- |
| `isTrusted` | boolean 或 enabledCommands 精确保留源块必要语义；不得扩大白名单；生成块始终不可信 |
| `baseUri` | 相对链接基准不改变；无法保持时整容器/整片回退 |
| `supportHtml` | 源块仅使用原有值且不包含生成文字；不能借切片让原本无效 HTML 获得新能力 |
| `supportThemeIcons` | 图标语法保持源行为，不让模型输出主题图标 |
| 引用定义 | 定义和使用必须处于同一有效解析作用域；不能随意复制定义到每个分片 |
| 列表/引用/表格 | 拆分 MarkdownString 可能重置编号或改变边距；AST 成功解析不等于可见排版正确 |
| 命令链接 | 链接文本、目标、参数和允许执行范围与原来源一致；只在自有测试夹具中验证导航 |
| 合并输出 | 没有丢失、重排或重复签名、代码示例、普通段落和特殊块 |

禁止以删除特殊链接、整体提升 trust、扩展允许协议、将模型文字写回受信任对象换取通过。

### 2.4 用例矩阵

| ID | 输入 | 期望 |
| --- | --- | --- |
| F01 | 真实 Java 普通摘要 + 独立 linked-throws 块 | 至少摘要可译；throws 链接仍可导航且只出现一次 |
| F02 | Java 同段 prose + command 链接 | 初版保留整段；不为提高覆盖破坏链接 |
| F03 | 列表/引用容器内部特殊链接 | 容器保留或证明闭合；编号/缩进不变 |
| F04 | 跨块 reference definitions、重复 label | 不改变引用作用域；无法封闭则整片回退 |
| F05 | Python Pylance 隐藏 moduleHash 与普通说明 | 不出现可见注释、不丢说明、代码保护不退化 |
| F06 | TS 泛型签名 + 表格/重载说明 | 签名、顺序与表格完整；两种显示方式成立 |
| F07 | 相对链接/baseUri、enabledCommands、themeIcons | 元数据与原交互一致；不安全拆分退回 |
| F08 | 模型返回命令链接/HTML、标记破坏 | 输出被拒绝；原文可靠返回，不获得新执行能力 |
| F09 | 多块超过 maxChars | 统一预算、完整段落停止；不通过拆块绕预算 |
| F10 | 共享任务/取消/切模式/缓存重用 | 既有生命周期不退化，后台无重复请求 |

F01/F05/F06 需要真实语言服务与可见 Hover；全部用例先通过确定性结构测试。链接验证限自有无副作用导航目标，不能执行任意来源命令来证明保真。

### 2.5 决策门槛与停止条件

**通过：** F01 有实质覆盖改善，F01–F10 的安全、结构、顺序、预算和生命周期要求全部满足；Windows 真实 Java 及至少 Python/TS 之一有 UI 证据。所有仍不支持的混合结构明确回退。

**有条件通过：** 仅某种独立顶层块可靠，其他容器全部回退；可建议只支持该窄范围的 0.5.x，必须明确覆盖边界。

**不通过：** 必须提升信任、删除链接、复制整片、依赖私有 DOM，或无法保持引用/列表/表格语义才能获得改善；立即结束该候选方案，不继续泛化解析器。

建议验证分两步：先以 F01–F04 判定分片原则是否成立，再扩到 F05–F10。第一步失败就输出结论，不为完成清单继续扩大实现。

候选验证文件：现有 `takeoverHoverContent.ts`/`markdownCodec.ts` 的隔离候选实现、`test/unit/takeover.test.ts`、`test/integration/languages.ts`、新公开夹具。最终是否替换生产函数另行设计。

## 3. G5：译文完成后自动刷新 Hover

### 3.1 第一问题不是如何触发，而是能否证明归属

当前公共 Hover 契约没有通用持续更新事件；编辑器管理鼠标与悬浮窗口。provider 曾收到某 URI/位置和 token，不能证明返回后该窗口仍然可见或属于该目标。[官方 API](https://code.visualstudio.com/api/references/vscode-api#HoverProvider)

第一道门槛：在允许的 API 范围内，能否可靠区分以下状态？

- 原目标 Hover 仍可见。
- 用户按 Esc 关闭，光标仍停在同一位置。
- 鼠标移开，但插入光标未动。
- 同一文档已改为另一个符号的 Hover。
- 同一文档在拆分编辑器或 Notebook 中存在不同目标。

若找不到可观察的可靠信号，直接输出“当前能力边界下不实施”。不能把文档未编辑、窗口有焦点、selection 未变、取消 token 未触发，拼成未经证实的可见性判断。

### 3.2 API 核验与能力范围

按验证时安装的 VS Code 版本核对类型声明、官方文档及对应源码；记录具体版本和证据，不只引用滚动 main 分支。

1. 先查公共扩展 API 是否有可见 Hover 身份、关闭事件和合法更新入口。
2. 如果只有 Proposed API 能提供能力，单独报告其 proposal、启用条件与稳定回退；是否允许扩大实验依赖另行确认，不自动纳入已有接管设置。
3. 如果仅编辑器私有控制器/DOM/CDP 能识别，视为产品方案不可用；测试观察能力不等于扩展 API 能力。

`editor.action.showHover` 可以由用户主动触发，但其存在不证明后台知道应该何时调用。它也不是“只更新现有窗口、绝不新建窗口”的原子 API。[官方命令实现](https://github.com/microsoft/vscode/blob/main/src/vs/editor/contrib/hover/browser/hoverActions.ts)

即使已经判断可见，从判断到刷新之间仍可能发生关闭；第二道门槛是更新入口能否避免此竞态。只有读取状态、随后强制 showHover 的方案不足以通过。

### 3.3 如果能力门槛通过，才进入行为验证

拟议必要条件（不是宣称已能实现）：刷新操作绑定窗口/编辑器/文档版本/位置或范围/单元格/模式代际/任务 ID；只使用已完成有效译文，不发起新网络；刷新前权限和目标仍有效；操作不能重开被关闭窗口。

不增加“完成后等待 X 毫秒再刷新”之类时序猜测；不模拟鼠标移动，不先 hide 再 show，不改 selection 把 Hover 移回旧符号，不循环刷新直至看到中文。

| ID | 用户动作/竞争场景 | 必须观察到 |
| --- | --- | --- |
| R01 | 停留同目标，延迟成功 | 当前窗口内容更新一次，无额外 HTTP |
| R02 | 请求期间 Esc 关闭 | 完成后不重开 |
| R03 | 鼠标移开，插入光标未动 | 完成后不重开 |
| R04 | 同文档 A→B，A 晚到 | B 不被 A 内容覆盖 |
| R05 | 切文件或拆分编辑器 | 不在新编辑器/另一侧打开旧目标 |
| R06 | 文档编辑/标签关闭 | 不更新失效版本，不重开标签 |
| R07 | Notebook 同单元格换位置/跨单元格 | 单元格与位置归属正确 |
| R08 | 两请求乱序、同请求多订阅 | 只刷新所属有效窗口，不重复 HTTP |
| R09 | 窗口失焦、切模式、暂停、撤回同意 | 不抢焦点；取消后不再更新 |
| R10 | 缓存命中、显示方式切换 | 不抖动、不出现旧模式译文；无额外网络 |
| R11 | 可见性检查后立刻关闭 | 无“检查时可见、执行时重开”的竞态 |
| R12 | 普通及无障碍模式 | 无产品主动 selection/focus 变更，记录原生无障碍行为 |

测试使用受控完成闸门，先精确触发动作再释放译文，避免仅靠偶然时间延迟。每个竞态至少覆盖关键事件顺序；额外重复运行用于发现抖动，不能用多次成功代替能力证明。

记录原文/译文呈现时间、是否重开、目标身份、selection/focus 前后状态、provider 调用数和 HTTP 数。观察原生 provider 重算与网络重发是两项不同指标。

### 3.4 决策门槛

**通过：** 有可说明的 API 契约支持身份与关闭语义；R01–R12 在声明支持的平台版本上成立；关闭竞态被设计解决，零自动重开、零产品主动焦点/选择变化、零额外 HTTP、无旧内容闪回。

**有条件通过：** 仅明确版本/实验 API 支持；必须独立可选并有稳定回退，后续再决定产品范围。不能因既有“实验接管”授权就假定用户同意所有新私有能力。

**不通过：** 缺可见性/目标信号，或刷新入口无法保证不重新打开。保留 G1 的完成反馈和主动查看；不添加 SSE 或强制 showHover 掩盖问题。

**环境不足：** 缺真实 UI 或目标版本；只归档缺口，不宣称通过，也不进入安装包。

候选验证文件：现有 integration renderer/接管测试的独立入口、控制完成顺序的 fake translator、必要的独立 API 能力记录。源代码只有验证通过且架构获选后才接入生产。

## 4. 验证产物模板

每项分别写报告，不合并成“整体实验通过”：

```text

日期、代码基线、OS / VS Code / 语言服务版本：
假设与允许的 API 边界：
实现候选及文件范围：

UI 证据、结构断言、请求计数：

结论：通过 / 有条件通过 / 不通过 / 环境不足
```
