# 悬浮翻译下一阶段路线图（讨论稿）

日期：2026-11-02（Asia/Shanghai）\
当前基线：`87179c6a391a81a3876088a935a6136af05d9808` / 0.4.0\
用户已选择：**优先打磨悬浮翻译的等待体验、配置诊断、译文质量。**

本轮只做探索和规划，没有修改生产代码、测试或安装包，也没有调用真实云端 API。下面的版本和范围均为建议，不代表已经批准实现。主代理核验本地实现与官方资料，三个独立只读代理分别探索产品现状、审查最新提交、研究对标产品。

## 1. 推荐方向

下一阶段建议以 **“翻译过程看得懂、没有译文查得清、文档译得更可靠”** 为主题。

0.4.0 已经完成主要语言与 Notebook 的第一轮扩展；继续增加语言不是眼下的首要收益。当前更直接的体验问题是：看到英文时，用户不容易知道是仍在等待、已经失败、权限不够，还是为了保留链接而主动跳过。

建议将 **0.5.0** 控制为三个目标：

1. 翻译状态与等待反馈，附带明确的光标处文档查看入口。
2. 本地配置诊断与用户主动发起的固定样例连接测试。
3. 代表性文档质量基线，以及针对证据明确问题的有限提示词/结构改进。

复杂 Java 文档的安全分块翻译作为独立探索项；达到安全与保真验收后再纳入0.5.x，不成为0.5.0的无限延期项。自动原地刷新、术语表、选区翻译、多服务切换等保留候选，暂不全部装入同一版本。

## 5. G1：等待体验与主动查看

### 建议交互

继续使用一个简短状态栏入口“悬浮翻译”，详细原因放鼠标提示或菜单。不要把“中文翻译”“完整原文”等大标题放回Hover，也不要为每次悬停弹通知。

| 场景 | 用户可理解的反馈 | 可用动作 |
| --- | --- | --- |
| 等待语言服务 | 正在读取文档 | 等待；需要时查看诊断 |
| 等待请求额度 | 正在排队 | 等待；查看原因 |
| 云端处理中 | 正在翻译 | 暂停自动翻译 |
| 接管已先回原文 | 正在后台翻译 | 继续阅读原文 |
| 已有可用缓存 | 译文已就绪，重新悬停查看 | 手动查看光标处文档 |
| 无原文/无可译文字 | 当前没有可翻译的文档说明 | 检查语言服务/光标位置 |
| 内容保真跳过/预算不足 | 部分内容保留原文，提示可查看原因 | 查看本次诊断 |
| 服务错误或冷却 | 用明确中文说明错误和恢复方法 | 修正配置/等待冷却/执行允许的重试 |

该设计与官方建议的轻量状态栏进度一致。[状态栏指南](https://code.visualstudio.com/api/ux-guidelines/status-bar)

新增动作建议命名为 **“悬浮翻译：查看光标处文档翻译”**，明确针对插入光标，而不是假定鼠标此前悬停的位置。优先复用现有请求和缓存：已有进行中任务就等待同一任务，不重新消耗额度；已有译文则查看它。首次失败可以提供受控重试，但仍遵守401配置阻断、429冷却与同意状态，不通过清空所有状态实现“重试”。强制丢弃有效缓存重新翻译可后置。

### 验收

- 受控延迟覆盖：预算内完成、超过2.5秒后完成、超时、排队、冷却、取消、无原文、保真跳过。
- 接管后台成功后能看到可理解的就绪反馈；不自动重新打开已关闭Hover、不移动光标、不抢焦点。
- 重复查看同一有效文档不会额外发起HTTP请求；缓存命中与等待共享任务可区分。
- 快速切换文档、位置、Notebook单元格时，不把旧请求的完成/失败显示成新目标的结果。内部递归采集和其他扩展触发的Hover查询不能制造误导性“当前鼠标状态”。
- 显示与请求服务状态分离，状态更新不触发缓存清空或限流解除。
- 先记录采集、排队、网络、渲染/交付阶段的本地耗时，再制定延迟目标；不无依据承诺p95，也不把源采集时间算成模型耗时。

## 6. G2：配置与问题诊断

分成两个明确动作，不需要先建设复杂设置Webview。

**本地诊断（默认不联网）：** 检查实际生效模式、实验权限回退原因、是否暂停、是否受信任本地环境、当前文档是否支持、endpoint/model是否完整、Key是否存在（仅布尔状态）、云端同意、阻断/冷却状态。语言服务检测只报告可观察证据：没有Hover不能武断判定语言服务未安装。

**测试当前服务（用户主动执行）：** 用固定公开短句测试当前endpoint/model/key是否能完成本插件所需的JSON/占位符协议。明确展示目标接口、发送内容和可能费用；没有必要把当前项目文档发出去。一次动作最多一个有上限的测试请求，重复点击合并，继续遵守取消、HTTPS、禁止重定向及既有限流策略。缺少授权时走明确的同意步骤，不在启动/配置输入时偷偷探测。

### 验收

- 无配置、缺Key、未同意、401/403/404、429、网络失败、超时、非兼容JSON、合法响应均有可操作解释。
- 模拟服务覆盖大多数分支，不需要付费请求验证错误分类。
- 本地检查零HTTP请求；真实连接测试仅在显式触发且授权满足后请求。
- 一键复制诊断摘要可包含版本、平台、模式、分类状态和耗时；不包含Key、请求/响应原文、源码或完整文件路径。接口地址/模型等需明确展示和脱敏策略，复制前可见。
- 服务修复后的状态能恢复为可用，不长期停留在旧错误；成功反馈来自实际结果，不能仅凭“输入完成”判断连通。

## 7. G3：译文质量与已支持场景验收

将三类问题分开统计，避免把“JSON能解析”当成“译文准确”：

1. **覆盖率**：应该翻译的段落中，哪些因预算、过滤、复杂标记或服务失败保留了英文。
2. **结构正确性**：标记顺序、代码/签名、参数名、链接、列表与表格是否保持。
3. **语义质量**：条件、否定、默认值、返回值、异常语义是否准确，是否捏造说明、术语是否前后一致。

建议先建约30个非敏感代表性样本，而不是建立大规模自动评分平台。包括用户已提供的 `builtins.str` 构造说明，Python参数/异常/生成器，JS/TS泛型/重载/JSDoc，Java参数/返回/带链接的异常说明，以及Notebook同单元格/跨单元格。公共样本需记录来源和许可；能用自写夹具表达的结构边界优先自写。

先通过本地假传输检查结构与回退，再在用户明确同意的样本/请求或费用上限内做少量真实DeepSeek验收。记录实际模型名、请求日期、配置、冷热缓存、耗时、结构成功率、人工语义判定；本轮不执行。真实API结果有波动，不适合将固定字符串译文作为自动测试唯一标准。

### 质量改进的最小策略

- 先收集错译样本，再针对“否定/条件被遗漏、术语漂移、标识符改写”等问题调整内置文档提示。
- 对标有文档专用模板与按模型定制能力，但本项目不能直接开放任意系统提示替换，破坏JSON/标记保护契约。[上游提示模板](https://github.com/YiiGuxing/TranslationPlugin/blob/bb50b0f4debe5464ffe99ede63c95e5456862bb7/src/main/kotlin/cn/yiiguxing/plugin/translate/trans/openai/prompt/PromptService.kt#L21)
- 调整提示或保护协议时同步缓存版本，避免旧译文使效果评估失真。
- 首个质量版本不同时叠加自动重试、语义改写、摘要、多模型兜底；无法验证的输出继续保留原文。
- 若错译主要集中于少数术语，再设计小型偏好表。未核实对标有独立术语表模块，此项是本项目自己的候选方案。

### 验收与证据补齐

- 所有选定结构样本都有明确期望，代码/签名/占位符无损坏，恶意输出不获得HTML或命令执行能力。
- 人工语义检查发现的严重错译要修复或明确列为未解决限制；不能用少量样本宣称普遍准确率。
- 补Windows当前版本测试及Java/TS/Notebook可见Hover断言，与macOS记录分开报告；缺少运行环境时明确留空，不能用mock补作真实验证。
- 参数、返回值、异常、默认值与条件是质量检查重点，不以压缩篇幅为目的删除内容。

## 8. G4/G5：两项高价值但需验证的探索

### 复杂分片：先从一类真实Java文档开始

当前`command:java.open.file`可能让整个Javadoc分片原样保留。推荐验证：能否在不重建特殊交互节点的情况下，把同一分片中独立的普通文字块译出。

- 首先选择现有Java带异常链接样例；不先实现通用HTML翻译器。
- 原始交互节点保留原有权限和位置关系，模型生成的文字仍严格不可信。
- 不能把翻译内容写入受信任MarkdownString；仅按节点拆分也不自动保证正确，需验证列表/引用/链接引用定义和排版连续性。
- 失败时继续保留原片段并解释原因，不降级为删除链接或放宽URL白名单。
- 只有实际Java和至少一个Python/TS结构样本同时通过可见UI、链接保真和安全验证，才建议纳入发行；否则保留为探索结果。

### 自动刷新：先做独立小验证，保留手动可靠路径

成功门槛包括：只刷新仍相关的目标、不重开用户已关闭的Hover、不抢焦点、不抖动、不启动重复翻译，兼容Notebook单元格与多请求并发。公共API不一定提供足够的可见Hover归属信息，因此验证可能得出“不值得实施”。不要让流式请求或强制`showHover`成为未经验证的默认行为。

## 9. 推荐实施顺序与范围控制

| 阶段 | 交付结果 | 完成后可做出的决定 |
| --- | --- | --- |
| A：基线与状态定义 | 文档样本、回退分类、阶段耗时定义、Windows/可见UI缺口清单 | 知道真正的等待与漏译原因 |

| D：独立技术探索 | G4安全分块、G5自动刷新各自形成通过/不通过结论 | 决定0.5.x范围，失败不拖累核心交付 |

后续实现可复用的文件边界（仅供估算，不是最终类设计）：

- 状态反馈：`src/ui/diagnostics.ts`、两个Hover provider和`src/translation/translationCoordinator.ts`；只引入必要的本地状态事件，不建遥测平台。
- 主动入口与诊断：`src/ui/commands.ts`、`src/extension.ts`、`src/config/*`，复用CredentialStore/ConsentStore；必要时拆一个小诊断服务。
- 质量：`src/translation/chatCompletionsClient.ts`、`src/content/*`、现有单元/集成夹具；缓存版本随语义协议更新。
- 回归：现有`test/integration/{languages,notebook,takeover,display}.ts`及安装冒烟；新增断言须针对用户结果，不复刻实现。
